Claude API は 2026 年 10 月 9 日にベータ版として、GitHub Copilot は 2026 年 10 月 1 日 (日本時間では 10 月 2 日) にパブリックプレビューとして、どちらも「ダイナミックワークフロー」という仕組みを公開しました。この記事では、まず自分の用途にどちらが合うかを決めます。そのあと、有効にして最初の 1 本を動かすまでを順に説明します。

先に要点をまとめます。

- **Claude API**：ベータ版ヘッダーと `multiagent` フィールドを設定します。
- **GitHub Copilot**：app は設定不要で、Copilot CLI は最新版で `--experimental` または `/experimental on` を使って試験的機能を有効にします。

## ダイナミックワークフローとは？Claude API と GitHub Copilot はどの場面で選ぶ？

ダイナミックワークフローは、複数のエージェントに任せる段取りをプログラムにして動かす仕組みです。Claude Managed Agents のエージェントにワークフローを書かせてサーバー側で動かすなら Claude API、Copilot CLI・GitHub Copilot app・GitHub Copilot SDK で自分が書くか Copilot に書かせた手順を動かすなら GitHub Copilot を選びます。

Claude API 側で公式に挙がっている用途の例は、数百件の文書のレビューだけです。Copilot 側は、段階・チェック・上限をはっきりさせたいタスクも例に挙げています。多数の対象をレビューする例は、両方の製品に共通しています。どちらが優れているかは、公式情報からは判断できません。

違いの一つは、ワークフローを書く主体です。Claude API では、Claude Managed Agents のエージェント自身がワークフローを書くことができます。エージェントは、たくさんのエージェントを段階に分けて走らせ、最後に結果をまとめるプログラムを書きます。そのプログラムは、サーバー側でバックグラウンドの「ワークフロー実行」として動きます。

GitHub Copilot では、開発者がオーケストレーションをコードで定義します。Copilot にワークフローを書かせることもできます。GitHub はコードで定義する理由を、複雑なマルチエージェントの作業に要る信頼性と可観測性を得るためと説明しています。

## Claude API でダイナミックワークフローを有効にするには？

ベータ版なのでヘッダー `managed-agents-2026-04-01` が必要です。また、有効にするかどうかはエージェントごとに `multiagent` フィールドで決めます。前提：Claude Managed Agents のエージェントで使う機能です。手順は次の 3 つです。

1. ベータ版ヘッダー `managed-agents-2026-04-01` を付ける
2. エージェントの `multiagent` フィールドに、下の JSON を設定する
3. システムプロンプトに、いつワークフロー実行を始めるかを書く (エージェントを導くため、とリリースノートは案内しています)

2 で設定する値は次のとおりです。

```json
{"type": "multiagent_20261001", "workflows": {"type": "enabled"}}
```

:::message
Claude Platform のリリースノート (October 9, 2026) には、システムプロンプトに書く具体的な文面の例は載っていません。ワークフロー実行の詳しい仕様は、リリースノートが詳しい説明の参照先に挙げている Workflow runs のドキュメントで確かめてください。
:::

## multiagent の type とベータ版ヘッダーを取り違えないためには？

置く場所ごとに文字列を分け、接頭辞と日付の書き方で見分けます。`type` に入る `multiagent_20261001` と、ベータ版のヘッダー `managed-agents-2026-04-01` は、どちらも日付を含む別々の文字列です。

| 置く場所 | 文字列 |
| --- | --- |
| ベータ版のヘッダー | `managed-agents-2026-04-01` |
| `multiagent` フィールドの `type` | `multiagent_20261001` |

見分けるときは次の点を見ます。

- ヘッダーは `managed-agents-` で始まり、日付がハイフン区切りです。
- `type` は `multiagent_` で始まり、日付が区切りなしです。

## Claude API のワークフロー実行はどう追跡する？

各ワークフロー実行は、セッションのイベントストリームに流れる `workflow_run.*` イベントで追跡します。エージェントを動かし始めたら、このストリームを見ていきます。

:::message
リリースノートに載っていない点もあります。個々のイベントの種類と中身、それに実行を途中で止める方法と再開する方法です。
:::

## Copilot CLI でダイナミックワークフローを有効にするには？

Copilot CLI を最新版にしてから、試験的機能を有効にします。GitHub Copilot app を使う場合は、設定なしで常に使えるので、この節は飛ばしてかまいません。ダイナミックワークフローは、すべての Copilot プランで使えます。

### 1. CLI を最新版に更新する

試験的機能を使うには、最新版の CLI が必要です。手元の CLI が古い場合は、次の `/update` を実行して更新します。

```text:Copilot CLI の対話セッション
/update
```

### 2. 試験的機能を有効にする

方法は 2 つあります。どちらか 1 つで足ります。

- CLI を起動するときに `--experimental` を付ける
- 起動済みの対話セッションで、次を実行する

```text:Copilot CLI の対話セッション
/experimental on
```

:::message
パブリックプレビューの間は仕様が変わる可能性があると、GitHub の Changelog に書かれています。
:::

## Copilot で最初のワークフローを作って確認するには？

Copilot に、普段繰り返している作業の段取りを伝えて、ワークフローにするよう頼みます。細かい作り方は、GitHub Changelog の告知からたどれる公式ドキュメント「Creating a dynamic workflow」で確かめられます。

### 作る前に知っておくこと

書き始める前に、コードとエージェントの役割を分けておきます。どの手順を順番に、どれを並列に動かすか、いつエージェントを呼び、その結果をどう使うかはコードに書きます。分析や判断が要る部分はエージェントに任せます。書いたプログラムは Copilot の拡張機能の中に置かれるので、Copilot の拡張用 API も使えます。

自分で書くときも、Copilot にワークフロー全体を書かせるときも、Copilot に組み込まれた作成ガイドを使えます。段取りを考えるときは、告知に挙がっている次の機能を組み合わせます。

- 外とのやり取り：コマンドを実行し、ツールやほかのサービスを呼ぶ
- 分割と並列：目標をタスクに分け、互いに独立したタスクは同時に動かす
- 段階の間の受け渡し：構造化した結果を次の段階に渡す
- 相互の確認：サブエージェントどうしで調査結果を確かめ合う
- 人の入力：クライアントが対応していれば、利用者に入力を求める
- 止めて確認：チェックポイントで一時停止し、結果を見てから再開する

### 最初の 1 本を Copilot に頼む

題材には、毎回同じ段取りで動かしたい作業を選びます。ここでは、告知に挙がっているサービス障害の調査を使います。

まず、試験的機能を有効にした Copilot CLI か GitHub Copilot app で、Copilot に段取りを伝えて作成を頼みます。次の文面は公式の例文ではありません。告知の例の 3 段階をそのまま並べた依頼の一例です。

```text:Copilot への依頼
サービス障害の調査をダイナミックワークフローにしてください。
1. ログとテレメトリを集める
2. 独立したエージェントに、それぞれ別のシステムを分析させる
3. 構造化した調査結果を、タイムラインと根本原因のレポートにまとめる
```

告知によると、このワークフローは実行するたびに同じ手順で動きます。

告知にはほかに、プルリクエストで変更された多数のファイルを並列にレビューする例や、リリースチェックを実行して失敗の評価を 1 つのエージェントに任せ、人の確認のために一時停止する例も挙がっています。

### 作ったワークフローを確認する

作成済みのワークフローを確認するときは、Copilot に次のように尋ねます。

```text:Copilot への質問
What dynamic workflows are available?
```

### 不具合や要望を送る

動かしてみて不具合や要望があれば、Copilot CLI で次を実行して送れます。

```text:Copilot CLI の対話セッション
/feedback
```

## ワークフローを使わず通常のチャットで足りるのはどんなとき？

GitHub Copilot は、すぐに答えが欲しいときや簡単な変更であれば、通常のチャットモードでプロンプトを送るだけで足りることが多いとしています。

判断の目安は次のとおりです。

- すぐに答えが欲しいときや簡単な変更 → 通常のチャット
- 同じ段取りを何度も繰り返す作業 → ワークフロー
- 時間がかかり、費用も大きくなりうる実行を途中で止めて後から再開したい → Copilot のワークフロー (公式の使いどころの例に挙がっています)

なお、任せ方と並列の調整を Copilot に委ねる `/fleet` と違い、ダイナミックワークフローはコードで定義した手順を毎回そのとおりに動かしたいときの仕組みです。
